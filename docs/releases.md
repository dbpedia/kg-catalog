# Monthly KG Catalog metadata releases

The repository contains a workflow for publishing **monthly snapshots of KG Catalog metadata** in GitHub Releases. This is distinct from releasing the catalog software or from releasing underlying KG datasets.

## Why publish a catalog release?

Snapshots make the evolution of the catalog visible and analyzable: which KGs are included, which source descriptions changed, and which published Databus/MOSS resources appeared or changed between captured states. They provide reproducible metadata extracts with provenance and checksums.

## Location, cadence, and naming

- **Location:** [GitHub Releases for `dbpedia/kg-catalog`](https://github.com/dbpedia/kg-catalog/releases)
- **Workflow:** [`.github/workflows/monthly-metadata-release.yml`](../.github/workflows/monthly-metadata-release.yml)
- **Schedule:** First calendar day of each month at 06:17 UTC (scheduled execution can be delayed)
- **Tag format:** `kg-catalog-YYYY-MM`, for example `kg-catalog-2026-11`
- **Title format:** `DBpedia KG Catalog — November 2026`
- **Manual:** GitHub Actions → *Monthly KG Catalog metadata release* → *Run workflow*; leave `publish` unchecked for a dry run

The workflow refuses to overwrite an existing published monthly release. The first snapshot is explicitly marked a **baseline**, not an assessment of historical changes.

## Sources in a release

| Collection inside ZIP | Source | Typical contents |
| --- | --- | --- |
| `kg-source-metadata/` | YAML from the checked-out GitHub revision | Original `metadata.yaml` files and provenance manifest |
| `kg-release-metadata/` | Live DBpedia Databus | RDF descriptions of KG groups, artifacts, and versions |
| `kg-level-metadata/` | Live DBpedia MOSS | RDF/Turtle KG-level metadata and provenance |

Source exports are generated by `scripts/export_yaml_catalog.py`, `scripts/fetch_databus_catalog_fixed.py`, and `scripts/fetch_moss_catalog.py`. The current MOSS exporter defaults to `https://moss.dev.dbpedia.link` and must be reviewed before describing its output as coming from a production MOSS environment.

## Generated assets

A successfully published release includes:

```text
GitHub Release: kg-catalog-YYYY-MM
  kg-catalog-YYYY-MM.zip  # Metadata snapshot archive
  SHA256SUMS.txt          # SHA-256 of that archive
  Release notes          # In GitHub Release description
```

The ZIP includes the three metadata collections, plus:

- `catalog-summary.csv`: one row per KG in the captured snapshot for longitudinal analysis.
- `changes.json`: machine-readable added/removed/modified resources compared with the previous monthly release, or a baseline marker.
- `ANALYSIS.md`: definitions and correct interpretation of summary/change fields.
- `release-info.json`: source revision, capture time, source systems, counts, workflow provenance, and comparison status.

Each metadata collection also contains its own provenance files, such as manifests, checksums, and discovery queries. See the `ANALYSIS.md` inside an actual release archive for field-level semantics.

## Interpreting a snapshot correctly

**Metadata only:** The archive does not contain KG RDF dumps or other underlying dataset payloads. Follow the distribution links or use the [download guide](https://kg-catalog.dbpedia.org/download.html) to retrieve KG data.

**Not an atomic snapshot:** GitHub, Databus, and MOSS are exported sequentially. A KG can change while the workflow is running. The generated snapshot therefore reflects a collection run, not a perfectly simultaneous timestamp across services.

**Changes vs. publication dates:** A newly observed version URI does not prove that its underlying dataset was created in that month. Version metadata timestamps may refer to Databus publication, not to original KG releases.

**Validation can fail:** The builder checks consistency among metadata sources. If an export is incomplete or the coverage sets differ, the release is refused rather than silently publishing a misleading archive.

## Running and verifying a release

1. Open [GitHub Actions](https://github.com/dbpedia/kg-catalog/actions/workflows/monthly-metadata-release.yml).
2. Select **Run workflow** with `publish` **unchecked** to create a dry-run candidate.
3. Download the generated Actions artifact and inspect the release notes, ZIP manifest, CSV summary, and change report.
4. Investigate mismatched KG coverage or unavailable services before attempting publication.
5. Run again with `publish` checked, or let the next scheduled release execute, once the candidate is validated.
6. Verify the published Release contains `kg-catalog-YYYY-MM.zip` and `SHA256SUMS.txt` and that its notes reference the correct month and source revision.

To verify a downloaded archive locally from the directory containing both assets:

```bash
sha256sum -c SHA256SUMS.txt
```

On macOS, `shasum -a 256 -c SHA256SUMS.txt` is also available.

## Separate metadata and software versioning

Catalog snapshots use calendar-based IDs (`kg-catalog-YYYY-MM`). Code releases and tags can follow their own versioning scheme. Do not conflate a snapshot's month with a semantic software version or a KG publisher's dataset version.

Operational details and failure recovery are in [Operations](operations.md).
